# IM异步编程入门与改造注意事项

这份文档是专门写给“还没有真正写过异步代码，但准备把 IM/WebSocket 这一层往异步方向演进”的自己看的。

目标不是一下子把所有异步理论讲全，而是先回答这几个最实际的问题：

- 什么叫同步，什么叫异步
- 为什么 Netty 天然更适合异步
- 为什么把接口改成 `Async` 不是改个名字就结束
- 你现在这个 IM 项目里，哪些地方会受到影响
- 第一次做异步改造时，到底要重点考虑什么

---

## 1. 先说结论

异步编程最核心的变化，不是“用不用 `Future`”，而是：

**你不能再默认“这个方法返回时，事情已经做完了”。**

同步代码的直觉是：

1. 我调用一个方法
2. 它做完
3. 成功就返回，失败就抛异常
4. 我再写下一行

异步代码的直觉是：

1. 我调用一个方法
2. 它只是“发起了这件事”
3. 真正的成功/失败结果，稍后才回来
4. 我必须在回调、future、promise 里处理结果

这一点，是所有后续复杂度的来源。

---

## 2. 什么是同步

先看同步代码的感觉。

例如现在这种风格：

```java
try {
    connection.sendText(payload);
} catch (Exception ex) {
    connectionRegistry.unregister(userId, connection.getId());
}
```

它的直觉非常简单：

- `sendText(...)` 调用结束时
- 我就知道这次发送成功还是失败
- 如果失败，当前 `catch` 当场处理

同步代码最大的优点就是：

- 时序直观
- 错误处理直观
- 新手更容易理解

但它的问题是：

- 如果底层操作很慢，当前线程会被卡住
- 在 Netty 这种 EventLoop 模型里，阻塞 I/O 线程很危险

---

## 3. 什么是异步

异步代码的核心感觉是：

- 先发起
- 后拿结果

例如以后如果接口改成：

```java
CompletionStage<Void> sendTextAsync(String text);
```

调用方式会更像：

```java
connection.sendTextAsync(payload)
        .whenComplete((unused, ex) -> {
            if (ex != null) {
                connectionRegistry.unregister(userId, connection.getId());
            }
        });
```

这里和同步最大的不同是：

- `sendTextAsync(...)` 返回时，不代表真正发送完成
- 真正完成，要等 `whenComplete(...)`
- 真正失败，也是在回调里感知

所以异步的关键不是“换了一个新 API”，而是：

**错误处理、状态更新、日志记录，都要延后到结果回来时再做。**

---

## 4. 为什么 Netty 更天然适合异步

Netty 发送消息时，天然给的是：

```java
ChannelFuture future = channel.writeAndFlush(...);
```

这意味着：

- 发送动作已经发起
- 但不是立刻完成
- 结果要通过 `future` 再判断

这和 Netty 的整体模型是一致的：

- I/O 线程负责事件驱动
- 不希望长时间阻塞
- 更希望把“完成结果”用 future 或 listener 传出来

所以 Netty 不是“异步更高级”，而是：

**它的底层 API 本来就是按异步结果模型设计的。**

---

## 5. 为什么 Spring WebSocket 会让你感觉不那么异步

Spring WebSocket 里你更常见的是：

```java
session.sendMessage(new TextMessage(text));
```

这个方法从使用感觉上更像同步调用：

- 调就调了
- 成功就返回
- 出错就抛异常

这不代表 Spring 完全不能做异步，而是：

- 它没有像 Netty 那样天然给你一个 `ChannelFuture`
- 所以如果你想在公共抽象里统一成异步语义
- Spring 这边需要自己“包一层”

例如：

```java
CompletableFuture<Void> future = new CompletableFuture<>();
try {
    session.sendMessage(new TextMessage(text));
    future.complete(null);
} catch (Exception ex) {
    future.completeExceptionally(ex);
}
return future;
```

所以：

- Spring 不是不能异步
- 只是没有 Netty 那么“原生 future 化”

---

## 6. 为什么“把接口改成异步”不只是升级接口

这是最容易低估的地方。

比如你现在把：

```java
void sendText(String text) throws Exception;
```

改成：

```java
CompletionStage<Void> sendTextAsync(String text);
```

变化不会只发生在接口文件上。

真正变化的是：

- 什么时候知道成功
- 什么时候知道失败
- 什么时机删除坏连接
- 什么时机记日志
- 什么时机打埋点
- 什么线程里执行回调

也就是说：

**接口签名改的是表面，调用时序改的才是本质。**

---

## 7. 你这个 IM 项目里，哪些地方会被异步改造影响

按你当前结构，主要会影响下面几层。

### 7.1 连接抽象层

这些类最先受影响：

- `ImSessionConnection`
- `SpringSessionConnection`
- `NettySessionConnection`

这是入口，因为发送和关闭语义先从这里变化。

---

### 7.2 推送层

这些地方现在大概率还是按“同步发送、同步捕获异常”的思路写的：

- `MessagePushServiceImpl`
- `ConversationWindowPushServiceImpl`

如果改成异步，就不能再直接依赖：

```java
try {
    connection.sendText(payload);
} catch (Exception ex) {
    ...
}
```

而要改成：

- 发送后挂回调
- 在回调里决定是否注销连接
- 在回调里记失败指标

---

### 7.3 清理和关闭层

例如：

- `ImWebSocketHeartbeatCleanupTask`

现在你可能默认：

- `close(...)` 调完就算关闭完成

如果以后改成异步关闭：

- 关闭 frame 发出去和 channel 真正关闭不是同一个时刻
- 清理逻辑就要重新理解“发起关闭”和“关闭完成”的区别

---

### 7.4 指标与日志层

比如这些问题都要重新想：

- 发送成功率是按“发起发送”统计，还是按“future 成功完成”统计
- 发送失败到底记在调用点，还是记在回调里
- 日志打印时，是否还能假设“下一行就表示已经发完”

---

## 8. 第一次写异步代码，最应该考虑的 8 件事

下面这些是最重要的。

### 8.1 成功和失败在哪里拿结果

同步时代码里，结果在当前调用栈。

异步时代码里，结果通常在：

- `whenComplete`
- `handle`
- `exceptionally`
- `listener`

你要先明确：

**这个操作最终成功/失败，是在哪个回调里决定的。**

---

### 8.2 失败以后谁负责清理

例如发送失败后：

- 要不要 `unregister`
- 要不要记日志
- 要不要打失败指标
- 要不要重试

同步里这个逻辑经常写在 `catch` 里。

异步里则要明确：

- 是发送方自己回调里处理
- 还是封装成统一工具方法处理

---

### 8.3 回调在哪个线程执行

这点非常重要。

你要知道：

- 回调是在 Netty EventLoop 线程执行
- 还是在业务线程池执行
- 还是在调用发起线程继续执行

如果这个点不清楚，就很容易：

- 阻塞 I/O 线程
- 并发改共享状态
- 发生你自己也看不懂的时序 bug

---

### 8.4 调用顺序是否仍然成立

同步时代码通常默认：

1. 先发送
2. 再写日志
3. 再做下一步

异步后可能变成：

1. 发起发送
2. 立刻继续执行下一步
3. 过一会儿才收到发送完成回调

所以你必须重新判断：

- 哪些代码必须等结果回来再执行
- 哪些代码可以先往下走

---

### 8.5 会不会重复清理

异步下很容易出现这种问题：

- 发送失败回调里 `unregister`
- 关闭事件回调里也 `unregister`
- 心跳清理线程也在删

这不一定是错，但你要确保：

- 多次删同一条连接不会出大问题
- registry 的接口是幂等安全的

---

### 8.6 会不会出现竞态

常见竞态包括：

- 发送刚发起，连接同时被关闭
- 关闭刚发起，心跳线程又来清理
- 两个线程同时对同一连接写数据

异步代码最常见的问题不是“语法不会写”，而是：

**多个事件谁先谁后，不再绝对可控。**

---

### 8.7 是否需要重试

异步后你会更容易考虑重试，但不是所有操作都该重试。

例如：

- 向一个已经坏掉的 WebSocket 连接发消息
- 通常不该盲目重试很多次

所以你要先想：

- 失败是否可重试
- 重试是否会造成重复推送
- 重试的收益是否大于复杂度

---

### 8.8 日志和指标打在哪一层

同步里容易写成：

```java
connection.sendText(payload);
log.info("send success");
```

异步里这就不可靠了。

更合理的是：

- 发起发送时记一次 debug/info
- future 成功完成时记 success metric
- future 失败完成时记 error metric

也就是：

**日志和指标的位置，要跟着结果时机一起变化。**

---

## 9. 你最容易踩的几个坑

### 9.1 只是把方法名改成 `Async`

这是假异步改造。

如果上层还是按同步思维写：

- 期待方法返回时事情已完成
- 在下一行就假设发送成功

那只是换了个名字，思维还没变。

---

### 9.2 在异步框架里偷偷阻塞

比如 Netty 里：

```java
future.syncUninterruptibly();
```

这能工作，但会把异步又拉回同步等待。

短期做适配可以，长期不理想。

---

### 9.3 回调里再写很重的逻辑

如果回调是在 I/O 线程里执行，而你又在里面：

- 查数据库
- 调 MQ
- 做复杂业务逻辑

那问题会重新回来。

所以异步不代表“哪里都塞回调”，而是要继续考虑线程职责。

---

### 9.4 忘了统一接口语义

如果 Spring 下：

- `sendText(...)` 是同步成功/失败

而 Netty 下：

- `sendText(...)` 只是发起发送

那同一个抽象接口在两种实现下行为不一致，会很危险。

所以如果走统一抽象：

- 语义最好统一
- 不然至少要显式分成同步接口和异步接口

---

## 10. 你现在这个项目，第一次异步改造最推荐的顺序

不要一上来全项目同时改。

更稳的做法是：

### 第一步：先理解“发送结果时机”

先明确：

- 当前哪些代码依赖“发送立刻知道结果”
- 哪些地方以后必须改回调式处理

这一步先做认知准备。

---

### 第二步：决定公共抽象是否升级

核心问题是：

- `ImSessionConnection` 是不是要改成异步接口

这是总开关。

如果这里不改，Netty 端就只能继续做同步包装。

---

### 第三步：先改连接层，再改推送层

顺序建议：

1. `ImSessionConnection`
2. `SpringSessionConnection`
3. `NettySessionConnection`
4. `MessagePushServiceImpl`
5. `ConversationWindowPushServiceImpl`
6. `ImWebSocketHeartbeatCleanupTask`

先从最中心的发送/关闭能力开始，不要从外围乱改。

---

### 第四步：最后再补日志、指标和清理语义

异步接口改完之后，再统一看：

- 发送成功率怎么统计
- 失败率怎么统计
- 坏连接什么时候清掉
- 关闭动作的指标打在哪

这比一开始就全想清楚更容易落地。

---

## 11. 对当前自己的建议

如果你是第一次认真接触异步代码，我建议：

- 不要把“异步”理解成高级语法
- 把它理解成“结果延后回来，所以时序和错误处理方式变了”

只要你先把下面这句话真正理解透，就已经进步很大：

**异步代码里，方法返回通常只代表事情开始了，不代表事情已经完成。**

把这句话吃透后，再回头看：

- `CompletionStage`
- `ChannelFuture`
- `whenComplete`

就不会那么抽象了。

---

## 12. 一句话总结

异步改造最难的不是 API，而是思维切换：

- 从“调用即结果”
- 变成“调用只是开始，结果稍后回来”

你现在这个 IM 项目如果以后真要往 Netty 异步模型靠，重点不只是改接口，而是把：

- 发送结果处理
- 失败清理
- 时序理解
- 线程职责

这几件事一起重新想清楚。
