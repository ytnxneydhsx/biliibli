# 监控系统改造计划

生成时间：2026-04-21 14:06:50 Asia/Shanghai

## 背景

当前 IM 压测分析主要依赖以下方式：

- 压测脚本手动采集 RabbitMQ 队列状态
- 手动导出应用 `/actuator/prometheus`
- 手动导出 MySQL `performance_schema` 与 `mysql.slow_log`
- 临时执行 `docker stats`、`jstack`、`rabbitmqctl` 等命令

这套方式可以完成单次定位，但存在几个问题：

- 采样步骤分散，重复劳动多
- 无法自然形成统一时间轴
- 容易漏掉压测中间的瞬时峰值
- 很难长期对比不同版本的趋势
- 对 CPU、线程、MQ、Redis、MySQL 的联动分析不够直观

因此需要建设一套可复用的统一监控系统，减少手工采样成本，并支持后续 IM 链路性能调优。

## 目标

本次改造目标如下：

- 建立一套基于 `Prometheus + Grafana` 的统一监控方案
- 覆盖应用、RabbitMQ、Redis、MySQL、Docker 容器、宿主机资源
- 支持压测时实时观测与压测后复盘
- 尽量复用现有 `Spring Boot Actuator + Micrometer` 指标
- 不影响现有业务链路和压测脚本

## 方案选型

建议采用以下组件：

- `Prometheus`
  用于统一抓取各类 metrics
- `Grafana`
  用于可视化展示与压测复盘
- `cAdvisor`
  用于采集 Docker 容器 CPU / 内存 / IO / 网络指标
- `node-exporter`
  用于采集宿主机资源指标
- `mysqld-exporter`
  用于采集 MySQL 运行指标
- `redis-exporter`
  用于采集 Redis 运行指标
- `RabbitMQ Management / Prometheus metrics`
  用于采集队列长度、consumer 数、publish / ack / redeliver 等信息

## 监控范围

### 1. 应用层

复用现有 `/actuator/prometheus`，重点关注：

- `im_db_operation_duration_seconds_*`
- `im_mq_consumer_duration_seconds_*`
- `im_mq_consumer_errors_total`
- `im_mq_publish_*`
- `im_ws_handshake_*`
- `im_ws_*`

建议后续补充更细粒度埋点：

- `ensureRedisConversationBaseline`
- `cacheConversationWindowBaselineIfAbsent`
- `projectConversationWindowEvent`
- `pushSingleConversationUpdated`
- `ImWebSocketOutboundSender.sendToUser`

### 2. RabbitMQ

重点关注：

- `im.message.persist.queue`
- `im.message.conversation.queue`
- `im.message.conversation.redis.queue`
- `im.message.recent.cache.queue`
- `im.message.realtime.queue`

关键指标：

- 队列消息数
- `ready` / `unacked`
- consumer 数
- publish rate
- ack rate
- redeliver rate
- dead-letter 情况

### 3. Redis

重点关注：

- `ops/sec`
- `connected_clients`
- `used_memory`
- `commandstats`
- `keyspace`
- Lua 调用情况
- 网络吞吐

如果后续需要进一步诊断窗口缓存链路，建议重点观察：

- `evalsha`
- `hget`
- `hset`
- `zadd`
- `sadd`
- `expire`

### 4. MySQL

重点关注：

- queries / commits / rollbacks
- threads connected / running
- InnoDB row lock waits
- deadlocks
- buffer pool 命中与脏页
- redo / fsync / file io
- slow queries

补充说明：

- SQL digest、wait event、slow log 统计依然保留在压测脚本内，作为补充分析材料
- 日常趋势监控由 exporter + Grafana 承担

### 5. 容器与宿主机

重点关注：

- `bilibili-app`
- `bilibili-mysql`
- `bilibili-redis`
- `bilibili-rabbitmq`
- `bilibili-nginx`

关键指标：

- CPU
- 内存
- 网络
- Block IO
- 宿主机 load
- 磁盘 IO

## 推荐目录结构

建议在仓库中新增一套独立监控目录：

```text
monitoring/
  docker-compose.yml
  prometheus/
    prometheus.yml
    rules/
  grafana/
    provisioning/
      datasources/
      dashboards/
    dashboards/
  exporters/
    mysql/
    redis/
    rabbitmq/
```

这样可以与业务 `docker-compose` 解耦，便于单独启动和维护。

## 实施步骤

### 第一阶段：基础观测面搭建

- 新增 `monitoring/docker-compose.yml`
- 接入 `prometheus`
- 接入 `grafana`
- 接入 `cadvisor`
- 接入 `node-exporter`
- 让 Prometheus 抓取应用 `/actuator/prometheus`

交付标准：

- 可以在 Grafana 中看到应用指标与容器 CPU / 内存曲线

### 第二阶段：中间件接入

- 接入 `mysqld-exporter`
- 接入 `redis-exporter`
- 接入 RabbitMQ metrics
- 在 Grafana 中建立 IM 链路 dashboard

交付标准：

- 能在统一面板里看到 app / RabbitMQ / Redis / MySQL 同步时间序列

### 第三阶段：业务埋点补强

- 为窗口缓存链路补充细分 Timer
- 为窗口推送链路补充 serialize / send 指标
- 为 baseline hit / miss 补充指标
- 为 MQ consumer deadlock / retry / rollback 补充细分标签

交付标准：

- 能直接判断窗口缓存链路中是 baseline、Lua、push 还是 outbound send 更慢

### 第四阶段：压测联动

- 将压测时间点与 Grafana dashboard 对齐
- 固定压测 dashboard 模板
- 后续压测只保留少量原始文件导出作为补充

交付标准：

- 压测复盘不再依赖大量手工命令采样

## 建议优先级

优先做：

1. `Prometheus + Grafana + cAdvisor + 应用 Actuator`
2. `mysqld-exporter + redis-exporter + RabbitMQ metrics`
3. 应用细粒度埋点补强

后做：

- 告警规则
- 长期容量基线
- dashboard 美化与多环境拆分

## 预期收益

完成后预期可以明显改善以下问题：

- 压测时不再依赖大量手工采样
- 能更准确识别首个瓶颈是 DB、Redis、MQ 还是 WebSocket push
- 能直接观察 `initkey`、窗口缓存、会话持久化等改动对整条链路的影响
- 更容易做严格 A/B 对比
- 后续定位死锁、线程争用、容器 CPU 打满等问题的成本大幅下降

## 当前判断

结合 2026-04-21 的压测结果，当前最值得优先支持观察的场景是：

- `single_conversation_persist` 是否因系统整体资源竞争而变慢
- `single_conversation_redis_projection` 开启后是否放大 JVM CPU 压力
- `pushSingleConversationUpdated` 是否导致额外 WebSocket 发送成本
- `initkey` 开启后是否将窗口缓存链路从“短路”变为“全量执行”

因此监控系统的第一版不应只关注数据库和 MQ，还必须覆盖：

- 应用容器 CPU
- JVM 线程与 GC
- WebSocket 相关业务指标
- RabbitMQ 队列积压
- Redis commandstats
