# 群聊功能设计说明（面向初学者）

## 1. 这份文档是干什么的

这份文档是给当前项目增加“群聊功能”的第一版设计说明。

目标不是一次把所有高级能力都做完，而是先做出一个：

- 能建群
- 能拉人
- 能退群
- 能发群消息
- 能看群历史消息
- 能在会话列表里看到群会话
- 支持群主、管理员、普通成员三种角色
- 支持踢人、禁言、改群设置

并且这个版本要尽量复用你现在项目里已经写好的 IM 主链路，而不是推倒重做。

---

## 2. 当前项目的 IM 现状

你的项目现在已经有一套“单聊 IM”基础设施，主要包括：

- 会话窗口
- 消息发送
- 消息历史
- WebSocket 实时推送
- RabbitMQ 异步派发
- Redis 会话/最近消息缓存

从代码上看，群聊并不是完全没有基础：

- `ConversationType` 已经有 `GROUP`
- `chat_conversation` 表设计里也给群聊预留了 `type=2`
- 当前 IM 的主线已经围绕 `conversationId` 运转，而不是完全写死成“两个人互发消息”

这说明：这个项目最适合采用“复用现有 IM 主链路，在其上补群资料、群成员、群管理层”的方案。

---

## 3. 最终选择的方案

本次选择的是：

## 方案一：复用现有 IM 主链路，在其上补“群资料 + 群成员 + 群管理”层

为什么选它：

- 最贴合当前项目结构
- 能复用已有会话窗口、历史消息、WebSocket、MQ、Redis 投影
- 对原有私聊功能影响最小
- 第一版更容易落地

不选的方案：

- 单聊和群聊完全拆两套系统：后续清晰，但第一版开发成本高
- 用多条单聊拼成伪群聊：虽然快，但后面几乎一定要重写

---

## 4. 需求边界

这次我们已经确定了群聊第一版的边界：

- 做“进阶群聊”
- 所有群成员都可以拉人入群
- 群主和管理员可以踢人、禁言、修改群设置
- 暂时不做入群审批
- 群聊复用现有会话模型，在会话类型里增加 `GROUP`

这几个边界很重要，因为它们会直接决定数据库结构、权限判断和接口设计。

---

## 5. 第一部分：整体架构怎么想

### 5.1 核心思想

群聊不要推翻现有 IM 主链路，而是在现有链路上扩展。

也就是说：

- 现有 `chat_conversation` 继续负责“每个用户视角下的会话窗口”
- 现有 `chat_message` 继续负责“消息事实记录”
- 新增 `chat_group` 存群本身的信息
- 新增 `chat_group_member` 存群成员关系和权限信息
- 新增 `chat_group_message` 存“某条消息在某个群里的群内递增序号”

这样做的结果是：

- 私聊照旧
- 群聊是新能力，但走同一套“发送 -> MQ -> 持久化 -> 窗口更新 -> WebSocket 推送”主链路

### 5.2 群聊里的四个核心对象

为了好理解，可以把群聊拆成四个对象：

1. 群本身
   - 群名、群头像、群公告、群主是谁、是不是全员禁言

2. 群成员
   - 谁在群里、谁是管理员、谁被禁言、谁已经退群

3. 群消息索引
   - 某条群消息在群内的第几条
   - 用于精确未读条数和群内顺序定位

4. 群会话
   - 每个成员在“消息列表页面”里看到的那个群聊天窗口

### 5.3 现有表如何继续使用

#### `chat_conversation`

继续保留，不重做。

群聊时：

- `type = GROUP`
- `target_id = groupId`

注意：会话窗口是“每个成员各有一条”，不是全群共用一条数据库记录。

#### `chat_message`

继续保留，不重做。

群聊时：

- 一条群消息只存一条记录
- 不要为每个成员复制一份消息
- 不直接把群专属的 `group_message_seq` 塞进公共消息表

这是一个很重要的设计原则。因为如果一条群消息复制成 N 份，后面历史消息、撤回、统计、排序都会变得很难维护。

#### `chat_group_message`

这是群聊读扩散里新增的一张关键表。

它的职责不是存消息正文，而是维护：

- `group_id`
- `server_message_id`
- `group_message_seq`

也就是说：

- 消息正文仍然在 `chat_message`
- 群内第几条消息，在 `chat_group_message`

这样做的好处是：

- `chat_message` 继续保持“单聊和群聊共用的公共消息事实表”
- 群专属的读扩散能力，不会把公共消息表塞胖
- 以后做精确未读条数时，可以直接基于群内连续序号计算

### 5.4 群聊里的角色模型

第一版建议：

- `owner`：群主
- `admin`：管理员
- `member`：普通成员

权限建议：

- `member`
  - 发消息
  - 邀请他人入群
- `admin`
  - 发消息
  - 邀请人
  - 踢人
  - 禁言成员
  - 修改群资料
- `owner`
  - 拥有管理员全部权限
  - 可以设置管理员
  - 可以转让群主
  - 可以解散群

第一版如果你想先收敛范围，也可以暂时不做“转让群主”和“解散群”，但表结构最好预留。

## 6. 第二部分：接口和消息链路怎么改

### 6.1 不要把群管理硬塞进现有消息接口

建议新增一组“群管理接口”，而不是把建群、踢人、设管理员都堆到已有消息控制器中。

建议新增：

- `POST /me/im/groups`
  - 创建群
- `GET /me/im/groups/{groupId}`
  - 查询群资料
- `GET /me/im/groups/{groupId}/members`
  - 查询群成员列表
- `POST /me/im/groups/{groupId}/members`
  - 拉人进群
- `DELETE /me/im/groups/{groupId}/members/{targetUid}`
  - 踢人
- `POST /me/im/groups/{groupId}/admins/{targetUid}`
  - 设置管理员
- `DELETE /me/im/groups/{groupId}/admins/{targetUid}`
  - 取消管理员
- `PUT /me/im/groups/{groupId}`
  - 修改群资料
- `PUT /me/im/groups/{groupId}/mute`
  - 设置全员禁言
- `PUT /me/im/groups/{groupId}/members/{targetUid}/mute`
  - 单成员禁言
- `POST /me/im/groups/{groupId}/leave`
  - 退群

### 6.2 发送消息接口不要再只认 `receiverId`

你现在的单聊发送模型，本质上是：

- 发送者是谁
- 接收者是谁

但群聊做出来以后，“消息目标”不一定是某个用户，也可能是某个群。

所以更推荐把发送消息的请求模型改成：

- `conversationType`
- `targetId`
- `clientMessageId`
- `messageType`
- `content`

含义是：

- 单聊时：
  - `conversationType = SINGLE`
  - `targetId = 对方 uid`
- 群聊时：
  - `conversationType = GROUP`
  - `targetId = groupId`

这样发送消息这个动作就统一成了：

> 给某个会话目标发消息

这比“永远只给某个用户发消息”更适合你现在的 IM 架构升级。

### 6.3 服务层发送链路应该怎么改

现在发送消息的主服务里，建议按下面的顺序处理：

1. 识别会话类型
   - `SINGLE` 或 `GROUP`

2. 做对应的权限校验
   - 单聊：继续走现有私聊权限校验
   - 群聊：校验发送者是不是群成员、是不是被禁言、群是不是全员禁言

3. 解析 `conversationId`
   - 单聊：继续使用现有规则
   - 群聊：新增稳定规则，比如 `g_{groupId}`

4. 构造统一的派发事件
   - 事件里不要再只强调 `receiverId`
   - 要改成“目标是人还是群都能表达”的模型

### 6.4 MQ 消费侧怎么分流

群聊上线后，MQ 消费逻辑一定要先看消息类型：

- 单聊消息：
  - 按原逻辑处理
  - 更新双方会话窗口

- 群聊消息：
  - 持久化 1 条群消息
  - 为这条消息分配群内递增序号
  - 写入 `chat_group_message`
  - 更新 `chat_group` 的群公共摘要和最新序号
  - 对在线成员做实时推送

这里最重要的点是：

- 消息只持久化一次
- 未读数不靠“给每个成员逐个加 1”
- 群未读数通过“群最新序号 - 成员已读序号”动态计算

### 6.5 WebSocket 推送如何兼容群聊

现有 WebSocket 协议不用推倒重做，但推送 payload 需要补充字段：

- `conversationType`
- `targetId`

这样前端收到后才能知道：

- 这条消息是单聊消息还是群聊消息
- 这条消息应该归到哪个会话中

### 6.6 前端状态模型必须升级

你当前前端消息页更偏向“按对方用户聊天”，比如很多状态围绕 `peerUid`。

群聊上线后，这个模型就不够用了，应该升级成“按会话聊天”。

建议前端用统一的会话 key：

- 单聊：`single:{uid}`
- 群聊：`group:{groupId}`

然后把当前页面中的：

- 当前聊天对象
- 消息列表分桶
- 窗口打开状态

都从“按人”改成“按会话”。

这是群聊前端改造里最关键的一步。

## 7. 第三部分：数据库、代码落点和开发顺序

### 7.1 数据库建议新增的表

#### 表一：`chat_group`

建议字段：

- `id`
- `group_name`
- `owner_user_id`
- `group_avatar`
- `announcement`
- `status`
- `member_count`
- `is_all_muted`
- `last_message`
- `last_message_time`
- `last_server_message_id`
- `last_message_seq`
- `create_time`
- `update_time`

这张表负责描述“群本身”。

#### 表二：`chat_group_member`

建议字段：

- `id`
- `group_id`
- `user_id`
- `role`
- `status`
- `mute_until`
- `last_read_seq`
- `invited_by`
- `join_time`
- `create_time`
- `update_time`

这张表负责描述“谁在群里、是什么身份、当前是不是被禁言”。

#### 表三：`chat_group_message`

建议字段：

- `id`
- `group_id`
- `server_message_id`
- `group_message_seq`
- `create_time`

这张表负责描述：

- 某条消息属于哪个群
- 这条消息在这个群里是第几条

可以把它理解成“群消息序号映射表”。

### 7.2 推荐的字段语义

为了后面好维护，建议明确约定：

- `role`
  - `1 = owner`
  - `2 = admin`
  - `3 = member`

- `status`
  - `1 = active`
  - `2 = quit`
  - `3 = kicked`

- `mute_until`
  - `null`：未禁言
  - 大于当前时间：仍处于禁言期

- `last_message_seq`
  - 这个群目前最新发到了第几条消息

- `last_read_seq`
  - 这个成员在该群里已经读到了第几条消息

群聊精确未读条数建议这样计算：

- `未读数 = chat_group.last_message_seq - chat_group_member.last_read_seq`

这里要特别注意：

- 不要直接用 `serverMessageId` 做相减
- 因为 `serverMessageId` 是全局雪花 ID，适合排序，不适合直接表示“这个群里多了几条消息”

### 7.3 现有表的改造原则

#### `chat_conversation`

尽量不大改。

群聊时直接把：

- `target_id`
- `type`

这两个字段用起来即可。

#### `chat_message`

也尽量不大改，但要确认代码语义统一。

特别要注意：

- SQL 里的 `conversation_id`
- Java 里的 `conversationId`

当前项目里这块已经有过一次演进，所以群聊接入时一定要让 `conversationId` 的规则稳定下来，避免后面 MQ、缓存、前端路由都出现不一致。

推荐：

- 单聊继续旧规则
- 群聊固定使用 `g_{groupId}`

同时建议坚持一个原则：

- `chat_message` 只存公共消息事实
- 群内连续序号放到 `chat_group_message`

这样可以避免把单聊/群聊共用消息表做得越来越臃肿。

### 7.4 代码结构建议怎么拆

建议新增 `com.bilibili.im.group` 模块，下面拆成：

- `controller`
- `mapper`
- `model.entity`
- `model.dto`
- `model.vo`
- `service`
- `service.impl`

它只负责：

- 建群
- 查群资料
- 查成员
- 拉人
- 踢人
- 设管理员
- 禁言
- 退群

### 7.5 群权限判断一定要单独抽层

建议新增一个单独的权限领域服务，例如：

- `GroupPermissionDomainService`

它负责回答这些问题：

- 某用户是不是群成员
- 某用户是不是管理员或群主
- 某用户现在能不能发消息
- 某用户能不能踢另一个人
- 某用户能不能邀请别人入群

为什么要单独抽出来？

因为如果权限判断分散在 controller、service、MQ consumer、WebSocket 推送里，后面会非常难排查 bug。

### 7.6 会话层需要补哪些能力

现有会话服务需要补群聊能力，例如：

- 为新群初始化成员会话窗口
- 新成员入群时补建会话窗口
- 成员退群或被踢后更新窗口状态
- 群消息到来时刷新群公共摘要
- 会话列表读取时，把群公共摘要和成员读进度拼装成群窗口视图

这里的关键变化是：

- 单聊窗口仍然偏写扩散
- 群聊窗口改成读扩散

也就是说，群聊不再要求“每来一条消息就给全员窗口逐个加未读数”。

### 7.7 最推荐的开发顺序

不要一上来就做“群消息实时收发”，那样最容易把私聊主链路一起改坏。

推荐顺序：

1. 先写 Flyway migration
   - 建 `chat_group`
   - 建 `chat_group_member`
   - 建 `chat_group_message`
   - 给 `chat_group` 增加群公共摘要和 `last_message_seq`
   - 给 `chat_group_member` 增加 `last_read_seq`
   - 补必要索引

2. 再做静态群管理
   - 建群
   - 查群资料
   - 查成员
   - 拉人
   - 踢人
   - 退群
   - 设管理员
   - 禁言

3. 再做群会话窗口
   - 群建好后，成员能在会话列表看到群

4. 再改消息发送主链路
   - 从“只支持单聊发送”扩成“支持单聊/群聊发送”

5. 再改 MQ 消费与实时推送
   - 群消息入库
   - 群消息分配 `group_message_seq`
   - 群公共摘要更新
   - 在线成员 WebSocket 推送

6. 最后改前端消息页
   - 从“按 peerUid 聊天”升级成“按 conversationKey 聊天”

### 7.8 最容易踩坑的地方

这里单独列出来，方便后面开发时反复对照：

- 不要把一条群消息复制成每人一条消息记录
- 不要直接用 `serverMessageId` 相减来算群精确未读条数
- 不要把群权限判断散落在多个地方
- 不要让前端继续只认 `peerUid`
- 不要第一版就做审批流、@提及、撤回、已读回执
- 不要让 `conversationId` 规则继续模糊不清

---

## 8. 给初学者的总结

如果你现在还是觉得复杂，可以把这次群聊改造理解成一句话：

> 不要重写 IM，而是在现有私聊系统上，再加一层“群是什么、谁在群里、谁有权限”的管理能力。

更具体一点：

- 会话系统继续用
- 消息系统继续用
- WebSocket 继续用
- MQ 继续用
- Redis 投影继续用
- 只是新增“群”“群成员”“群消息序号映射”三层模型

所以这不是另起炉灶，而是“在现有 IM 上长出群聊”。
